1. PRIORIDADE MÁXIMA — SEGURANÇA DO FIRESTORE [CONCLUÍDO EM 28/07/2026]
----------------------------------------------

Arquivo: firestore.rules

A regra genérica:

  match /users/{uid}/{document=**} {
    allow read, write: if request.auth != null
      && request.auth.uid == uid;
  }

também corresponde aos seguintes caminhos protegidos:

  /users/{uid}/private/subscription
  /users/{uid}/private/subscription/subscription_log/{logId}

No Firestore, regras que correspondem ao mesmo caminho são combinadas por
"OU". Uma regra mais específica não substitui nem restringe uma regra
genérica que já concedeu acesso.

Consequências possíveis:

- O cliente pode alterar o próprio plano ou status de assinatura.
- O cliente pode tentar se promover para Premium sem passar pelo backend.
- O cliente pode escrever ou adulterar o histórico da assinatura.
- O allow delete da assinatura permite apagá-la, recriar o estado gratuito
  e tentar iniciar um novo período de teste.

Ações recomendadas:

- Remover a regra recursiva genérica.
- Criar matches explícitos para cada coleção pertencente ao usuário:
  lançamentos, categorias, recorrências, metas, configurações etc.
- Manter subscription e subscription_log fora das permissões genéricas.
- Fazer exclusão de assinatura/conta por backend confiável, quando necessário.
- Criar testes automatizados das regras usando Firebase Emulator.
- Testar explicitamente que um usuário não consegue:
  - alterar plan ou subscriptionStatus;
  - alterar currentPeriodEnd;
  - criar logs de assinatura;
  - apagar e recriar a assinatura para repetir o trial;
  - ler ou escrever dados de outro usuário.

11. DESEMPENHO DOS TOTALIZADORES — IMPLEMENTADO EM 28/07/2026
--------------------------------------------------------------

Problema encontrado:

- A quantidade de lançamentos não era o principal fator de lentidão.
- O Dashboard fazia consultas dos dois meses e de recorrências.
- Depois aguardava uma segunda rodada para verificar instâncias recorrentes
  antes de exibir qualquer total.
- Quando uma recorrência era criada, ainda fazia uma terceira rodada.
- Falhas ou demora excessiva podiam deixar a tela carregando indefinidamente.

Melhorias implementadas:

- Os totalizadores agora dependem somente das consultas do mês atual e do mês
  anterior, executadas em paralelo.
- A sincronização das recorrências acontece depois que os valores já estão
  visíveis.
- Os totais são relidos somente quando uma recorrência realmente cria um novo
  lançamento.
- A verificação de vários meses passou a usar uma única consulta por intervalo.
- A tela de lançamentos também usa uma única verificação para todo o período.
- Foi adicionado timeout de 12 segundos ao Dashboard.
- Foi adicionada mensagem de erro com botão "Tentar novamente".
- Em desenvolvimento, o console informa o tempo dos totalizadores e o tempo
  da sincronização de recorrências.
- As páginas passaram a usar React.lazy e Suspense.
- Recharts fica no chunk da página de Relatórios.
- PDF.js só é importado quando uma importação PDF é iniciada.
- ProtectedRoute mostra LoadingScreen enquanto restaura a autenticação.

Resultado do build:

- Bundle principal anterior: aproximadamente 1,33 MB (347 KB gzip).
- Bundle principal depois: aproximadamente 781 KB (202 KB gzip).
- Relatórios ficou em um chunk separado de aproximadamente 406 KB.
- Dashboard ficou em um chunk separado de aproximadamente 13,5 KB.

Testes:

- Foi criado dashboardService.test.js.
- Os testes garantem que os totais não aguardam recorrências.
- Os testes garantem que dois meses usam uma única sincronização.
- Os meses só são relidos quando algo foi realmente gerado.
- Total atual: 50 testes passando em 3 arquivos.


12. CACHE DOS TOTALIZADORES — IMPLEMENTADO EM 28/07/2026
---------------------------------------------------------

Problema:

- O Firestore já possuía cache persistente em IndexedDB, mas getDocs aguardava
  a tentativa de obter dados atuais do servidor.
- Ao trocar ou revisitar um mês, o Dashboard limpava os indicadores e mostrava
  carregamento mesmo quando os dados já haviam sido vistos.

Solução implementada:

- Os helpers do Firestore agora aceitam leitura explícita do cache ou servidor.
- O Dashboard tenta pintar primeiro os dados persistidos no IndexedDB.
- Um resultado vazio do cache não é tratado automaticamente como saldo zero,
  pois também pode representar um mês nunca armazenado no dispositivo.
- Existe um cache em memória por usuário e mês para navegação instantânea
  durante a mesma sessão.
- A consulta do servidor acontece em paralelo e continua sendo a fonte final
  de verdade.
- Enquanto confirma os dados, a interface mostra discretamente "Atualizando…".
- Se o servidor estiver lento ou offline, os últimos dados conhecidos continuam
  visíveis.
- A sincronização de recorrências continua em segundo plano e atualiza o cache
  somente quando gerar lançamentos.

Comportamento esperado:

- Voltar para um mês já visitado: exibição praticamente instantânea.
- Reabrir o app: exibição rápida quando o Firestore tiver aquele mês no cache.
- Primeiro acesso a um mês nunca visitado: carregamento normal pelo servidor.
- Conexão lenta: dados anteriores permanecem visíveis enquanto são confirmados.
